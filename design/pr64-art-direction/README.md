## 游戏美术的实际构成

本轮使用内置imagegen分别生成三张原创1536×1024牌室背景，以及毛毡、皮革两张材质。原件、运行时WebP、生成提示和来源都在 `art/`。房间不是整张预烘焙UI：文字、牌点、花色、头像、金额与操作保持独立绘制，可按屏幕重新布局。

1. **远景**：真实房间的灯具、木质/金属、软装和景深；手机保留中轴裁切，长屏展示更多，短屏裁掉装饰。
2. **牌桌物体**：真实皮革纹理、可见缝线、厚桌沿、近景暗面、黄铜/玉白细边；桌布有细密毛毡纤维和柔和中心光，不是单色椭圆。
3. **牌与筹码**：卡牌有亮面、薄侧边、接触阴影和轻微扇形角度；筹码有边缘齿纹、层叠厚度、错落与阴影，金额仍独立显示。
4. **桌边角色**：保留现有原创角色，像桌边名牌而非后台卡片；姓名与筹码始终清楚，位置徽章独立摆放，避免UTG+1挤换行。
5. **事件光效**：最佳五张共同亮边，其他公共牌轻降亮；单手赢家有短暂绿金薄光束，普通赢牌与整局冠军金冠/撒花保持区别。
6. **次级页**：复盘、设置、记录继承绿黑材质与金属细边，但降低房间与纹理强度，让正文保持安静、清楚。

三个房间及材质均为原创，没有复制参考游戏的品牌、人物、Logo或节日装饰。现有角色插画、黑桃、字体和批准的音源继续复用。最终实现为分层美术，不依赖整张截图拉伸。

## 5–9人、不同屏幕怎么适配

设计使用实际内容窗口扣除状态栏、胶囊、手势区，再分配导航、局况、操作与桌区。所有人数独立验证，不用5人/9人推断6/7/8人。几何在 `scene-layout.mjs`，只处理视觉；正式实现应与既有共享 `compact-table-layout.js`、`rail-layout.js` 对接，不产生另一套规则。

| 类别        | 验证窗口                                                | 关键策略                                                                    |
| ----------- | ------------------------------------------------------- | --------------------------------------------------------------------------- |
| 最短窄屏    | 320×568 Web；320×568 SE App（20/0安全区）               | 去外层装饰边距；紧凑动作；隐藏泛化caption；无手势条的机型不画手势条         |
| 小手机      | 360×640 App；375×667 Web                                | 房间只作背景；快捷尺度在48px滑杆行内展开，不盖本人牌                        |
| 常规手机    | 390×844 Web；393×852 iOS（59/34）；393×852微信（88/34） | 公共牌3+2，48px主操作，真实系统区域独立预留                                 |
| 大手机      | 412×915 Android（28/24）                                | 增加可见空间，不无限放大座位或字                                            |
| 平板        | 768×1024（24/20）；1194×834（24/20）                    | 五牌单排；真实触摸控件仍48px，不按宽度假设鼠标                              |
| 桌面低高度  | 1280×720                                                | 公共牌48×68、紧凑桌边牌手、测量筹码实体和旋转牌面，保证本人牌型在动作区之上 |
| 常规/宽桌面 | 1440×1000；1920×1080                                    | 宽椭圆牌桌与右侧动态；桌宽限幅，房间向外扩展                                |

三方案共13尺寸×5人数=195种组合。`fit.html`提供每一种原图。给定数值是设计目标，真实App必须读取运行时safe area；不能把同一393×852总窗口与浏览器393×852内容区直接当相同可用高度。

### 不可妥协的前景约束

- 姓名/筹码至少11px，风格/公开行动至少10px；不通过整桌scale压小文字。
- 手机公共牌按空间为3+2，桌面/宽平板五张单排；卡牌与玩家实际区域保留净距。
- 主操作、设置入口、滑杆、尺度快捷、开关、选择器、重置等触摸区至少48px。图形可以小，真实命中区不能小。
- 本人手牌与筹码堆按**实体边界与厚边阴影**留间隔，不只测宽松父容器。
- 六/八人顶座居中时，底池文字和明细点击区必须避开该座位行动条；用真实字形与命中检测核对，不把底池提到座位上方反盖。
- BTN唯一，其下一顺时针依次SB、BB；只有当前行动者强调，按钮位置不跳动。
- 短屏尺度面板临时替换滑杆所在48px行，四个快捷值+关闭均48px；选值或Escape收起，不覆盖本人牌/公共牌/金额。

| 冠军、出局、补码        | 冠军金额与最终筹码一致；出局0筹码与下一局；补码在下一手前、独立计数       |

| 风格、座位、角色详情    | 原创八风格、现有角色与模型边界；绿黑阅读面板、完整名称                    |

## 36秒动效与声音

| 时间    | 可观看的实际变化                          |
| ------- | ----------------------------------------- |
| 0–3秒   | 两轮底牌从真实发牌锚点进入九人座位        |
| 3–6秒   | 公共牌从牌背、薄侧边到正面翻转            |
| 6–9秒   | 本人行动提示，价格与按钮保持稳定          |
| 9–12秒  | 筹码先停到各自桌内下注区                  |
| 12–15秒 | 街末筹码从下注区汇聚中央                  |
| 15–18秒 | 摊牌参与者亮牌，其余保持牌背              |
| 18–20秒 | 最佳五张与“A一对·Q踢脚”，短暂绿金赢家光束 |
| 20–22秒 | 中央筹码发给赢家，余额计数依引擎账本      |
| 22–25秒 | 原强起手牌紫光与稀疏微粒                  |
| 25–27秒 | 四类情绪图标与光环                        |
| 27–29秒 | 补码计数与浮起金额                        |
| 29–33秒 | 冠军金冠、双侧撒花                        |
| 33–36秒 | 出局灰卡和淡环                            |

用户新视频前段为大厅/买入等流程，末段牌桌仍在等玩家；**不能把本提案的发牌、下注、收池时序冒称参考片实测**。这些时序是NOIR的新增美术设计，参考截图提供赢家高亮/牌室纵深的视觉方向。

音源保持用户已批准的510ms“原视频节奏”筹码PCM、现有发牌/过牌/获胜提示、现有配乐与仪式声；不截取第三方视频声音。音乐2400ms渐入，动作期间不临时压低。减少动态模式移除飞行/翻转/放大/粒子/光束峰值，保留文字和静态结果；声音与振动独立。

## 跨端一致还原

1. 同一套WebP场景/材质、本地字体、向量牌点与图标；不可让系统emoji替代黑桃、齿轮、皇冠或情绪形状。
2. 文字、金额、牌面与按钮独立于背景；手机重排而不是把桌面整张缩小或拉长。新中文需沿现有脚本重新生成字体子集，Web/App完整11语言，微信只中文。
3. App使用包内资产，保持源/拷贝指纹；不设置远程`server.url`。选定后只打包所选方案，不要求同时携带三套。
4. 单套所用场景+两材质约0.7MiB，微信不能直接塞入当前已接近上限的主包；按既有本地分包机制规划美术包，开练前完成载入并核验。截图不证明微信包预算或真机性能已达标。
5. 所有特效依实际牌局/获奖者/合法动作触发，保留下一手、重打、重置和后台取消语义。计数与结算继续调用现有引擎。
6. 先Web还原，再Xcode/Gradle编译、安装版与微信DevTools/实体设备分别验收，比较同状态、同可用尺寸、同语言的原图；本轮没有把浏览器效果图计为这些运行通过。
